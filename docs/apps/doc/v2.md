# Doc 2.0

Doc 2.0 is a large change, developed on its own branch. It has two parts: a
tree that stores files where the owner keeps them, and Outlines rebuilt as an
explicit folder skeleton.

## Aim

A growing object store managed by its metadata. Objects are mostly added;
removing one is rare, for mistakes, and goes through the trash.

| Object store | Doc 2.0 |
|---|---|
| Object | a file, known by its SHA-256 whatever its name or place |
| Metadata | the sidecars in `_dgs/items/`, plain YAML |
| Key | the path the owner chose, recorded in the sidecar |
| Delete | the trash, once no Item names the object |

Unlike an object store, an object's name is a readable path chosen by the
owner, and the owner may edit a file in place.

## Storage

A new tree may use the [In place](layout.md#in-place) layout. In short:

- A file inside the root is recorded where it is; one from elsewhere is copied
  to a folder chosen at import, unless the same content is already
  [stored](#same-content-stored-once).
- A PDF made from photos goes directly in the chosen folder, named at import.
  Retained images keep their filenames in a sibling directory named after
  the PDF without `.pdf`; conflicts are refused.
  Already recorded files stay where they are when more revisions are added.
  Ordinary external revision files keep their
  original names in the chosen folder; name conflicts are refused. A suffix
  instead names a copy beside the current file.
- Everything doc keeps — marker, sidecars, definitions, trash — is under one
  visible folder, `_dgs/`; the root holds only the owner's files. Every
  sidecar is `_dgs/items/<item-id>.dgs-item.yaml`, and nothing else is there.
- A file moved by hand is found by digest and its new path recorded once the
  owner confirms. A file changed in place is handled by whether the Item is
  [locked](#locked-items); a plain file stays a file.
- Several Items may name one file; a file goes to the trash when no Item
  names it.

### Locked Items

An Item may be locked; its Template sets the default (identity papers and
contracts locked, references and notes not), and the owner may change it per
Item. A check meets a file whose digest changed at its recorded path:

- **Locked:** an error naming the file, to be restored from a backup. No
  revision is offered.
- **Not locked:** a new revision is recorded without asking; the earlier one
  keeps its fields and digest and is marked as having lost its file.

This replaces asking the owner each time. Template `locked: true` sets the
initial Item lock at import; omitted or `false` starts unlocked. It is the
Template's own setting, like `kind`, rather than an inherited field default.
Changing a Template does not change existing Items. The initial identity-card
Template created for an in-place tree is locked; by-Item initialization is unchanged.
Browse's Locked button changes an Item's setting.

Browse's **Check files** action records unlocked changes. Within one check, a shared file path is hashed once and every reference is compared with that result. The checked-file and byte counts report unique paths read; the next check reads them again. The CLI check stays
read-only and reports them. A lost snapshot keeps `path`, fields and digest
with `lost: true`; preview and export refuse to read newer bytes as that old
snapshot. Checks can find its original bytes elsewhere and offer a path to
confirm. Confirmation updates every reference to that digest within the Item,
clears its loss marker and preserves HEAD; another Item sharing the file has
its own confirmation. A lost file found nowhere can be accepted instead:
Browse's **Accept loss** marks every revision with that digest
`loss_accepted: true`, keeping its fields, digest, path and `lost: true`.
Checks stop reporting it unless its bytes are found again, when the path is
offered as before; confirming clears both markers. Retained original images are searched for moves too;
changed originals are errors to restore, rather than new PDF revisions.

The File check dialog uses the shared list table, with Item, recorded path,
result and found paths/confirmation columns. Columns can be resized, moved
and selected; long paths wrap in their cells. Each candidate has its own
confirmation button, and confirmed rows show the recorded path.

### Same content, stored once

An import first looks for its file's digest in the tree. When an object with
the same content is already there, the import offers to use it: the new Item
names the existing object, and nothing is copied or written. This holds for a
file from outside the root as for one inside it at another path, and a later
deletion counts the reference like any other.

### Versioning the metadata

The sidecars and definition folders under `_dgs/` hold only YAML, so the owner
may keep them under Git while the files stay out of it. `dgs` does not commit, and does not read
Git. A sidecar restored by Git that no longer matches the files on disk is
reported by the next check, not repaired. Two machines editing the same Item
conflict in Git, and the owner resolves it there.

## Files other than PDF

An object may be any file.

- **Images** may be made into a PDF, as photo imports are.
- **Other files**, such as video and audio, are stored as they are, with a
  thumbnail where the platform makes one natively (QuickLook on macOS; none
  elsewhere), kept in the local cache outside the tree, and a button that
  shows the file in Finder.
- **Page text, text search and page views** remain PDF-only.

Much of doc assumes an Item's file is a PDF: a revision's `paper`, the
extension in exports, the preview. Each becomes a file of any type.

## A new document or a new revision

- **A new revision** is the same paper: a rescan, or corrected fields. A
  corrected field changes only the sidecar.
- **A replacement** is a new paper: a renewed ID card or passport, with a new
  number and validity. It is a new Item that supersedes the old, chosen under
  "Replaces" at import, as today. The old Item is retired as superseded and
  keeps its sidecar and file; neither file moves.

## Outlines

Today an Outline lists rules, and each rule's path template, children and
numbering produce the folders. In practice:

- Numbering needs an order list per `{#}`, numbers monotonic with it,
  `numbers` patches, `{/#}` and `unlisted`; restarting numbers per country
  meant splitting a rule into children per country.
- The folder structure is spread across rules: what lies in one folder, or
  which number is free, is learnt by reading every rule.
- Items without a natural home are listed by ID in a catch-all rule, or
  reached through tags.
- Conditions grow long.

### Direction

Separate the skeleton from what fills it, and keep the Outline an assembly:
rules generate folders, Snapshots are fixed folders, and an Outline only
places them. An Outline never becomes a rule itself.

- **A rule writes a folder skeleton** with literal names. A number the owner
  chose (`05-Health`, `11-公证书`) is part of the name.
- **A folder takes Items** by type: `take`, with an optional `if` in today's
  expression language for what a type list cannot say. Both narrow what
  reaches the folders below. The folders below take first; a folder with
  `take` keeps what none of them took, so a deeper level is optional per
  Item.
- **`each` makes a folder per value or per anchor Item**: per owner, per
  issuer, or per tenancy, employment or vehicle, with the Items linked to it
  by `about` inside; an Item whose `about` names several anchors goes under
  each. Tags used only to group Items under an anchor are no longer needed.
- **`start` sets the first `{#}`** of the folders an `each` makes, so a
  sibling can continue a numbering, as `start: 3` after `01-计算机`. Only
  folders that hold something are numbered.
- **An Outline mounts rules and Snapshots** at folders, in order, and sets
  defaults its rules inherit. The same rule serves a "current" and an
  "expired" Outline that differ only in their defaults.
- **An Item lands in the first folder that takes it**, through the mounts in
  order and each rule top to bottom, deepest folders before their parent.
- **Items outside a rule or Outline are listed, folded,** instead of being
  caught by a catch-all rule. Each takes only what it is for, so Items
  outside it are expected, not a fault.

### Format

A rule is a list of folders, each an object with a `name`, never a mapping
whose keys are folder names: a folder could otherwise be called `take`, and
order is explicit. `defaults` are inherited down the tree and may be
overridden by any folder.

```yaml
# rules/identity.yaml
name: identity
folders:
  - name: '{#}-{owner}'
    each: owner
    order: [alice, bob]
    folders:
      - name: 01-CHN
        if: country == 中国
        folders:
          - name: 00-重要证照
            take: [id_card, passport, driver_licence]
            file: '{#}-{name}'
            order: [身份证, 护照, 驾驶证]
      - name: 02-AUS
        if: country == 澳大利亚
        folders:
          - name: 05-Health
            take: [insurance_policy]
            if: category == Health
```

```yaml
# rules/rental.yaml
name: rental
folders:
  - name: '{address}/{date.start}-{date.end}'
    each: tenancy
```

```yaml
# outlines/current.yaml
name: current
defaults: { revision: head, valid: today }
mount:
  - rule: identity
  - rule: rental
    at: 11-Rental
  - snapshot: alice-tax
    at: 01-alice
    as: 11-Tax
pins:
  01-alice/01-CHN/00-重要证照:
    items: [<item-id>]
    numbers: { 学位证书: 9 }
```

```yaml
# outlines/expired.yaml
name: expired
defaults: { revision: all, valid: expired }
mount:
  - rule: identity
```

### Pins

What the owner fixes by hand on the page is stored in the Outline, under the
path of the folder it concerns: an Item put in that folder, and a number
fixed for a name there. Where an Item lands and what number it bears is the
Outline's result, so the same Item may sit differently in two Outlines;
sidecars keep only what describes the Item.

### Numbering

Numbers are given only within one folder, by one key: an order list, the
date, or the owner's order on the page, then 01, 02 and on. A number may be
pinned on the page, stored as a line in that folder. There is no monotonic
requirement, no `{/#}` and no `numbers` patch. Revisions of one Item in one
folder share its number and are told apart by date:

```text
01-护照-2016.pdf
01-护照-2026.pdf
02-身份证-2019.pdf
```

### Revisions and validity

Each folder says which revisions it takes and how valid they must be,
replacing the rule-wide `selection: head|all`:

- `revision: head | all`: HEAD only, or every revision.
- `valid: today`: not past `date.end` (or without one), and not superseded.
- `valid: expired`: past `date.end`, or superseded.

A "current" Outline and an "expired" Outline mount the same rules with
`valid: today` and `valid: expired` as their defaults. The result follows the day of the
export: a card past its end moves from one to the other at the next export.

## Later

### Volumes

Not planned now; a long-term option.

A tree may register further volumes, known by their volume UUID rather than
their mount path. A file on a registered volume counts as inside the tree and
stays where it is; its sidecar path names the volume.

```yaml
# _dgs/tree.yaml
layout: in-place
volumes:
  media: { id: <volume-uuid> }
```

```yaml
# a sidecar's file
path: media:videos/2024/birthday.mov
```

While a volume is not mounted, its Items still show with their fields and
cached thumbnails, marked offline; show in Finder is disabled; a check
reports the volume offline and how many files it skipped, not missing files;
an export skips them and lists them. Once mounted again, under whatever
mount name, it is found by its UUID.

## Implemented folder contracts (V6–V8)

The marker chooses storage and Outline format independently: `layout` omitted
means by Item; `layout: in-place` records paths. `outlines` omitted or `paths`
selects Doc 1 rules; `outlines: folders` selects folder skeletons. All four
combinations are supported. Init offers both choices. Existing marker bytes
stay unchanged. Trees using folder skeletons save only the new formats. The page edits
folders and mounts with native controls; drag placement, owner order and fixed
numbers are saved in the Outline's `pins`. Trees using Outline version 1 retain Doc 1 formats;
a one-off conversion remains open.

Number allocation is shared by the final folder path across mounts, starts at
01 and reserves pinned numbers even when their named file is absent. A fixed
number can name a file's numbering key or an Item ID. Selected revisions of
one Item share their number. Multiple revisions receive a date suffix unless
the file pattern already includes a date; ambiguous dates use revision numbers.
Empty literal folders appear in the preview and are created by export.

`head` is the revision default; an omitted validity filter accepts any date.
Defaults inherit through the Outline, rule and folders; explicit folder values
win. `today` excludes superseded Items and revisions whose end date is before
the export day; `expired` selects those cases. Missing end dates remain current.
Group, Why here and export use the same placement and validity engine.

## Deferred

- **Convergence** — types that inherit, conditions as one `if` expression, a
  rule's paths nesting: built, and in [`index.md`](index.md). What is left is
  the one-off migration of the real tree. [`convergence.md`](convergence.md)
  keeps the reasoning.

- **Accounts on a server** — not decided. The same web pages served to several
  people, each seeing and editing only part of the Items.
  - Sign-in with accounts in a YAML file, password hashes only; HTTPS.
  - Access is per Item, not per folder: a generated tree is a view, and one
    Item appears in several. What a person sees is the tree built from the
    Items they may read.
  - An `acl` field on `record`, inherited by every type, holds groups, not
    people. A Template's `defaults` fills it when a PDF is added. Only an
    owner or an admin may change it.
  - `users.yaml` holds groups and a `policy` of `if` expressions per group,
    for access without touching sidecars.
  - Readers are the owner, the members of the groups in `acl`, and the
    groups a policy matches. Grants only add; there is no deny. Write access
    comes from policy only.
  - Every endpoint filters: search, Browse, an Item, its PDF, `/api/values`,
    `about` links (a link to an unreadable Item shows no content), export,
    Outlines, Snapshots. Templates and Rules are admin only.
  - Concurrent writers need a lock or a version check per sidecar; history
    events record who made them.
  - Shipped as the same `dgs` binary in a Docker image, run as a server mode
    of `dgs doc`, not as a second program.
  - Groundwork worth doing before: every Item read goes through one function;
    history events carry an `actor`; `internal/doc/expr` knows nothing of
    rules.

- **Integrity** — not decided. The PDFs are the data to protect, so the
  answer is at the file level, not a database: content addressing, atomic
  writes, `verify` and backups.
  - An operation touching several files (a move on a changed date, a merge)
    writes each file as a temporary, reads it back, then renames it, as Photo
    Import does. Steps are ordered new before old and are idempotent, so an
    interrupted run leaves at worst an extra file, which `verify` reports and
    a rerun finishes.
  - `verify` also checks fields: a required one missing, a value its type
    rejects, an `about` naming an Item the tree lacks. Run before and after
    the convergence migration.
  - `verify --deep` hashes every PDF again to catch bit rot. A server runs
    `verify` daily and `--deep` weekly, and reports what it finds.
  - A deleted or damaged PDF comes back only from a backup (NAS snapshots, an
    off-site copy); `verify` finds it, and its digest checks the restore.

- **Clone**, and the three-way merge a cloned sub-tree allows.
